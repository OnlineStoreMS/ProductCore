# 线上 / 线下双体系架构

> 业务顶层分为 **线上电商** 与 **线下门店（会员/俱乐部）** 两套体系，各自足够庞大，可独立演进；**ProductCore 商品库** 作为共享内核，串起线下选购与线上铺货的同一份货。

---

## 1. 为什么要拆成两套

| 维度 | 线上（Online） | 线下（Offline / Store） |
|------|----------------|-------------------------|
| **客户** | 平台匿名买家、公域流量 | 会员/俱乐部、私域、到店客户 |
| **触点** | 抖店/淘宝/小红书/闲鱼/视频号 | 门店、微信小程序、企微 |
| **订单** | 平台订单、平台规则、平台售后 | 门店收银单、小程序选购单、服务预约单 |
| **支付** | 平台代收 | 微信支付的商户号、POS 扫脸/扫码 |
| **履约** | 快递、WMS、打包视频 | 自提、现场交付、预约到店、维修工单 |
| **售后** | 平台 RMA、开箱视频、平台回传 | 门店保修、服务单进度、私域客服 |
| **运营** | 铺货、采购、多店电商 | 会员等级、积分、活动推送、俱乐部 |

强行塞进一个「大一统 OMS」会导致模型臃肿、迭代互相拖累。**拆开，用商品库和可选的会员/库存桥接。**

## 3. 两个独立「产品」，一个共享「货」

### 3.1 命名建议（逻辑分仓，可同 Monorepo）

| 系统 | 代号 | 边界 |
|------|------|------|
| 商品库 | **ProductCore** | 全公司唯一 SKU 主数据 |
| 线上电商 | **CommerceHub** | 平台订单 + 供应链 + 电商售后 |
| 线下门店 | **StoreHub** | 门店 + 会员 + 小程序 + POS + 服务 |

**部署上可以：**
- 初期：一个 Go monorepo，`internal/product` / `internal/commerce` / `internal/store`
- 成熟期：ProductCore 独立服务；CommerceHub、StoreHub 各独立部署，通过 API 读商品

### 3.2 管理后台怎么拆

| 后台 | 用户 | 菜单大致范围 |
|------|------|--------------|
| **Commerce Admin** | 电商运营、仓管、采购 | 商品(只读或双入口)、平台订单、采购、WMS、电商售后、追溯 |
| **Store Admin** | 店长、店员、俱乐部运营 | 门店、会员、活动、门店订单、服务单、POS 对账 |
| **Product Admin** | 商品管理员 | 商品库维护（或嵌入两者，但数据同源） |

商品编辑 **只维护一份**，Commerce / Store 侧都是 **读 ProductCore API**，避免两套商品。

## 4. StoreHub：线下体系设计

### 4.1 以会员/俱乐部为中心

```
                    ┌─────────────────┐
                    │   会员 / 俱乐部   │
                    │ 等级·积分·权益   │
                    └────────┬────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
   微信小程序              门店 POS            店员/店长端
   · 浏览商品(读ProductCore)  · 收银开单          · 核销/预约
   · 下单支付               · 会员识别          · 服务派工
   · 维修预约               · 挂单/退换(店规)    · 门店报表
   · 服务进度查询
   · 订阅消息/模板消息
        │                    │                    │
        └────────────────────┴────────────────────┘
                             ▼
                    StoreOrder / ServiceOrder
                             │
                    store_id · member_id · sku_id
```

**私域价值：** 小程序承载会员身份、预约、支付、进度推送；比纯 POS 更贴近「俱乐部」运营。

### 4.2 门店侧订单类型（与线上 OMS 分开）

| 类型 | 说明 | 是否走平台售后 |
|------|------|----------------|
| **store_retail** | 门店收银 / 小程序到店购 | 否，门店规则 |
| **store_pickup** | 小程序下单、门店自提 | 否 |
| **store_delivery** | 小程序下单、总部代发 | 可复用 CommerceHub 出库，仍归 Store 订单 |
| **service_appointment** | 维修/保养预约 | 服务单，非 RMA |
| **service_workorder** | 维修施工单 | 配件可扣 ProductCore SKU |

StoreHub 自有 `store_orders` 表，**不要**和 `orders`（平台电商）混表；需要时用 `order_type` + 不同服务边界。

### 4.3 微信小程序定位（C 端）

```
用户 ──► 微信小程序 ──► Store API (BFF)
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
          Member          StoreOrder      Service
          会员/积分        选购/支付        预约/进度
              │               │               │
              └───────────────┴───────────────┘
                              │
                    ProductCore API (只读)
                    商品列表/详情/SKU/价格策略
```

**BFF 层** 聚合接口，面向小程序契约，不直接把 Commerce 内部表暴露给 C 端。

小程序能力清单：
- 会员注册/登录（微信 openid + 手机号）
- 商品浏览（同步 ProductCore，可配门店价/会员价）
- 下单、微信支付
- 维修/服务预约
- 订单/服务进度、订阅消息
- 俱乐部活动、积分商城（后期）

### 4.4 门店 POS

- 场景：到店快速收银、会员刷卡/扫码识别、挂单
- 与小程序 **共享 StoreOrder 模型**，区别在 `channel=pos` vs `channel=mini_program`
- 离线弱网：POS 可本地队列，恢复后同步 StoreHub

## 5. 商品库如何串起线上线下

### 5.1 唯一货主：ProductCore

```
ProductCore (SPU/SKU 主数据)
      │
      ├──► CommerceHub：平台上架、采购、WMS、平台订单行
      │
      └──► StoreHub：小程序商品页、POS 扫码、服务配件
```

**同步方式：**
- Store / Commerce **不复制商品主数据**，只缓存 + **读 API**
- 可配置 **渠道可见性**：某 SKU 仅线下、仅线上、或两者
- 可配置 **价格策略**：ProductCore 基础价 + Store 会员价 / Commerce 平台价（存在各自模块，不回写主数据）

### 5.2 库存策略（推荐分阶段）

| 阶段 | 做法 |
|------|------|
| 初期 | 中心仓库存归 CommerceHub/WMS；门店只卖现货或不扣 central stock |
| 中期 | IMS 增加 `warehouse_type=central|store`，门店仓独立库存 |
| 打通 | 小程序「总部发货」单 → 触发 CommerceHub 出库；门店自提 → 扣 store 仓 |

**关键：** 无论哪条链路，`sku_id` 相同，追溯和报表才能合并。

## 6. 会员是否统一

线下以会员为中心，线上买家可能是陌生人 — 建议 **MemberHub 可选共享**：

```
member_profiles          -- 统一会员 ID（手机号/微信 unionid 合并）
member_channel_bindings  -- 微信 openid、平台 buyer_id（弱关联）
member_tiers / points    -- 俱乐部等级积分，主要 Store 写
```

- **Store**：会员是核心，小程序全量使用
- **Commerce**：平台订单默认不强制会员；若同一手机号购买，可 **归并到 member_id**，实现「线上买、线下来修」

不必一期全打通；先 Store 会员跑通，后期做 **手机号/unionid 归并**。

## 7. 线上 vs 线下：边界清单

| 能力 | CommerceHub | StoreHub | ProductCore |
|------|-------------|----------|-------------|
| 商品主数据 | 读 | 读 | **写** |
| 平台店铺订单 | **写** | — | — |
| 门店/小程序订单 | — | **写** | — |
| 采购/供应商 | **写** | — | — |
| 中心仓 WMS | **写** | 读/触发 | — |
| 门店仓 | 调拨 | **写** | — |
| 电商售后 RMA | **写** | — | — |
| 维修服务单 | — | **写** | 读 SKU |
| 会员积分 | 可选读 | **写** | — |
| 小程序 C 端 | — | **写** | 读 |
| 平台 API | **写** | — | 读 |

## 8. 跨体系协作场景

### 8.1 小程序下单、总部快递发

```
StoreHub: 用户小程序下单 + 支付
    → store_order (fulfillment=hq_ship)
    → 调用 CommerceHub API 创建 internal_ship_request
    → CommerceHub: 出库 / 物流 / 可选回写 store_order 运单号
    → 小程序推送：已发货
```

Store 拥有 **客户关系和支付**；Commerce 拥有 **仓和快递**。

### 8.2 线上购买、门店维修

```
CommerceHub: 淘宝订单 SO-xxx (sku_id=手机)
    → 会员归并后 member_id 关联
StoreHub: 小程序预约维修 service_order
    → 关联 member_id + 可选 ref_commerce_order_id
    → 服务进度推送
```

追溯：`trace_id` 可跨系统引用，或 Store 服务单记录 `ref_order_no`。

### 8.3 同 SKU 线下卖、线上也卖

ProductCore 一个 SKU；Commerce 平台上架；Store 小程序 + POS 可售；库存分池或共享，由 IMS 策略决定。

## 9. 项目结构（Monorepo 示例）

```
biz-platform/
├── cmd/
│   ├── product-api/       # ProductCore
│   ├── commerce-api/      # 线上
│   ├── store-api/         # 线下 + 小程序 BFF
│   └── worker/
├── internal/
│   ├── product/           # 共享
│   ├── commerce/          # online: order, integration, wms, aftersale...
│   ├── store/             # offline: store, member, pos, mini_bff, service...
│   └── shared/            # 公共工具、事件总线
├── web/
│   ├── commerce-admin/    # 电商后台（现有 Demo 演进）
│   └── store-admin/       # 门店后台（可后建）
├── miniapp/               # 微信小程序
└── docs/
```

成熟期可将 `commerce-api` 与 `store-api` 拆成独立仓库，**ProductCore 契约（OpenAPI）稳定即可**。

## 10. 分阶段建设（修订总路线）

| 阶段 | CommerceHub | StoreHub | ProductCore |
|------|-------------|----------|-------------|
| **P1** | — | — | 商品库 + Admin |
| **P2** | 供应商+WMS+采购 | 门店档案 | 商品 API 稳定 |
| **P3** | 平台订单+发货 | 会员+小程序(浏览商品) | 渠道可见性 |
| **P4** | 电商售后 | 小程序下单+支付+POS | 价格策略扩展 |
| **P5** | 多渠道 | 服务预约/维修单 | 库存分池 |
| **P6** | 追溯 | 私域推送/俱乐部 | 会员归并(可选) |

**两条线可并行**，只要 **P2 后 ProductCore API 稳定**，Store 小程序即可开始，不必等电商渠道全部接完。

## 11. 设计原则

1. **顶层分治**：线上 Commerce、线下 Store，各自 OMS/售后/触点独立
2. **商品唯一**：ProductCore 是唯一 SKU 源，线下选购与线上铺货 **同货**
3. **小程序是 Store 的 C 端**，不是电商平台的替代品；私域、会员、服务是它的主场
4. **跨体系用 API + 事件**，不要跨库 join 另一系统的表
5. **会员可先 Store 后归并**，不阻塞 Commerce 建设
6. **总部代发是协作点**，Store 订单触发 Commerce 履约，各保各的单据

---

## 12. 一句话总结

> **线上 CommerceHub 管公域平台与供应链；线下 StoreHub 管门店、会员俱乐部与小程序私域；ProductCore 管货。两套体系独立演进，通过 SKU 和可选的会员/库存/代发 API 串起来。**
